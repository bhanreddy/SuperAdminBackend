# Security review

Review date: 30 October 2026. Local source, HTTP and actual PostgreSQL/RLS validation; not a production penetration test or external security certification.

## Controls implemented and exercised

- Existing internal JWT/session authentication is reused. Connect requires `tokenSource=internal` and a validated internal session, rejecting legacy school/Supabase login even when its email matches an internal employee. CA/CA_LEAD and non-company employees are excluded. Roles and active status come from the current database.
- Every REST service transaction explicitly uses NOBYPASSRLS collaboration_api. API IDs and school context cannot grant membership. Server-local employee/company settings are transaction scoped, including under pooled connections. Multi-company tests cover the same employee enrolled in two organizations.
- Private channels require explicit membership for content. Founders can administer metadata/membership, but must explicitly join before reading. Direct messages require one of the immutable pair; founders cannot inspect other employees' DMs.
- RLS protects messages, replies, reactions, mentions, reads, notifications, files, pins, saves and task source links. Anon/authenticated public-schema grants are explicitly revoked on Connect tables. SECURITY DEFINER helpers use fixed search paths and restricted execute grants; browser clients cannot invoke privileged mutators.
- Conversation and message identity are immutable, cross-channel/nested thread parents are rejected, and composite foreign keys protect relationships. Message writes/mentions/notifications and sensitive administrative audits commit together. Audit failures abort administrative changes.
- Realtime tokens last 120 seconds, live only in memory, have a dedicated read-only role/purpose/company and bind to a current internal session/token version. RLS evaluates recipient/conversation access. No service key reaches the client; the same token cannot read unrelated internal_users/school data. Lease refresh is not message polling.
- Durable message IDs and per-message revisions deduplicate incoming events and prevent stale responses undoing deletions or reactions. Rejoin/foreground recovery reads durable history across every missed page. Account/cluster remount destroys cached messages/drafts and closes subscriptions; callbacks from an old scope are ignored.
- Full-text/message/channel/employee/mention search stays inside company and current conversation/DM permissions. Membership removal blocks history, search, notifications, mention choices and attachments immediately on the server.
- Requests use parameterized SQL, bounded UUID/text/date/query validation, a 2 MB existing JSON ceiling, per-employee transactional action limits, and bounded process-local attempt limits. Messages render as React Native text; no HTML interpretation. Links allow HTTP(S) without embedded credentials and do not cause server-side preview fetches (no SSRF preview service).
- Private file downloads reauthorize every request and return attachment bytes with no-store, nosniff and a restrictive CSP. No public/signed URL is returned. Uploads check size, extension/MIME/signature; images are decoded/re-encoded with sharp and pixel limits. Modern Office ZIPs are bounded before and during decompression and reject macros/embedded packages, traversal, encryption and local/central mismatches. Active PDF token checks reject obvious script/launch content. Upload retry is hash-deduplicated and failed DB writes attempt private object cleanup.
- Task conversion checks source membership, live employee, current delegation permission/overrides, school scope, assignee scope and assignee access to the source conversation. It inserts existing school_onboarding_checklists, not a new task platform. Only reviewed task wording is shared; original text is not automatically copied. Source link has separate internal RLS.

## Known limits and release gates

1. **Live authorization/realtime not yet verified.** Migrations, publication, Supabase custom-role grants and legacy JWT signing-key compatibility need testing in an explicitly selected staging project. PGlite tests PostgreSQL policies but does not emulate Supabase WAL delivery, its managed roles, Storage policies or every multi-backend/MVCC scheduling behavior. No production schema/key changes were made.
2. **Employee FCM delivery is unavailable.** This checkout has no employee token registry or sending provider. In-app notifications work and are deduplicated. Enabling push returns a clear configuration error; no test falsely reports device delivery. A real employee push integration must use the durable notification ID and revalidate recipients/preferences before sending, with client deduplication across delivery mechanisms. Lock-screen content should omit message bodies by default.
3. **File validation is not malware scanning.** Container/signature checks and download isolation reduce application-level risk, but do not certify arbitrary PDF/Office documents malware-free. No antivirus/CDR provider or native file-opening behavior was available. Validate a suitable scanning/quarantine process before allowing untrusted file sources in production. Orphan storage cleanup can fail during an outage and requires operational review; it never creates public access.
4. **Retention/legal hold is not approved.** Deletion leaves a content-free tombstone and metadata audit. Historical edit text is not retained. There is no legal hold or scheduled purge; do not represent either as implemented.
5. **Native performance not measured.** Web captures at desktop/mobile widths and renderer navigation tests passed; physical low-end Android, iOS sharing, keyboard behavior, background push, interrupted uploads and production load require real-device testing. Availability is an explicit expiring status evaluated when refreshed, not a continuously observed presence guarantee.
6. **Existing unrelated authentication regression failures remain.** The full backend suite has existing CRM/auth boundary failures, including email-binding and administrative-access cases. All 13 current failing test names were reproduced from the original Git HEAD in an isolated archive or corresponding missing external fixtures; baseline runs had additional failures too. Connect closes the legacy-login entry path locally, but does not repair or certify unrelated CRM authorization. Resolve/review those failures before asserting the entire SuperAdmin application is secure or regression-free.

## Excluded attack surface

No external workspaces, customer participants, arbitrary URL preview fetching, HTML messages, SVG/HTML/macro uploads, custom Slack assets, service-role browser access, audio/video/screen sharing, AI assistant, plugin marketplace or additional login system. Application administrators and database owners still have their existing privileged database access; RLS is not a protection against a compromised database administrator.

Local automated security checks passed for Connect. Overall production acceptance remains pending the gates above.
